# CiteQuest Retrieval Benchmark v1

## Purpose

Benchmark v1 establishes a reproducible retrieval baseline before any
reranker, Agent, MCP, HyDE, or multi-hop work. It compares:

1. BM25 lexical retrieval through SQLite FTS5.
2. Dense retrieval with BAAI/bge-m3 and FAISS.
3. The existing min-max score-fusion Hybrid retriever at alpha 0.5.
4. Tuned Hybrid retrieval, with alpha selected on development queries only.

No result is included in this document until the official run is complete.

## Status

The benchmark runner, metric tests, deterministic query-set builder, artifact
validation, and a small synthetic smoke run are implemented. The official
50,000-paper corpus and 150-query frozen set have not yet been built or run.

The existing peS2o indexes remain demo and full-text stress-test artifacts.
They are not the official quality benchmark and are not treated as
computer-science-filtered data.

## Official Corpus

- Source: arXiv computer-science categories downloaded through
  `scripts/download_arxiv.py`.
- Size: exactly 50,000 papers.
- Index location: `data/indexes/benchmark_v1/`.
- Search text: the existing title/abstract chunk generated by ingestion.
- Dense model: `BAAI/bge-m3`, 1024 dimensions.
- Storage: SQLite FTS5 plus local FAISS files.

Runs on 5,000 or 10,000 papers are development runs. They must be labelled
`smoke_or_development`, never Benchmark v1.

The separate 10k peS2o demo can be checked after its FAISS build with:

```bash
python scripts/run_demo_smoke.py
```

That command validates artifact consistency, warmed retrieval latency, and the
search/citation route handlers. Its generated report is labelled `demo_smoke`,
contains no relevance metrics, and is not an input to Benchmark v1.

`python scripts/run_http_smoke.py` is the complementary deployment smoke. It
starts a temporary Uvicorn process and verifies the same public routes over
localhost HTTP. Its output is also operational evidence, not retrieval-quality
evidence.

## Frozen Evaluation Set

`scripts/build_retrieval_eval.py` constructs
`data/eval/retrieval_v1.jsonl` once, then refuses to overwrite it unless
`--overwrite` is explicitly supplied.

- 150 target papers sampled with seed 42.
- 50 development queries and 100 test queries.
- 50 keyword, 50 natural-question, and 50 semantic-paraphrase queries.
- Target sampling is distributed across available source categories.
- Query-type assignment is balanced independently from category sampling.
- Target papers require a unique normalized title and at least 60 abstract
  words.
- One known relevant paper is recorded per generated query.
- Query generation uses temperature 0 and bounded validation/retries.
- Long title phrases and queries composed almost entirely of title words are rejected.
- Each record captures the generation model, temperature, and output-token budget.
- A `.partial` JSONL checkpoint makes API-backed generation resumable.

The test split is frozen and must not be used to choose alpha, candidate depth,
embedding settings, or any later retrieval parameter.

## Ranking Unit

Production retrievers return chunks. Evaluation operates on papers:

1. Preserve chunk result order.
2. Deduplicate by `paper_id`.
3. Retain the first, highest-ranked chunk for each paper.
4. Compute metrics on the resulting unique paper ranking.

Production retrieval behavior is not changed for the benchmark. The default
retrieval depth is 10, matching the reported `@10` metrics and normal API
candidate behavior.

## Metrics

- `HitRate@K`: 1 when at least one relevant paper is in top K, else 0.
- `Recall@K`: relevant papers in top K divided by all known relevant papers.
- `MRR@10`: reciprocal rank of the first relevant paper within top 10.
- `nDCG@10`: binary DCG normalized by an ideal ranking built from all known
  relevant papers.
- Latency: mean, p50, and p95 wall time across separately timed warm queries.

Each method receives one untimed warm-up query. Model and index cold start is
excluded from normal latency.

## Hybrid Selection Protocol

The lexical weight alpha is swept on the 50-query dev set:

```text
0.20, 0.35, 0.50, 0.65, 0.80
```

Selection order is:

1. Highest dev `nDCG@10`.
2. Highest dev `MRR@10`.
3. Earliest value in the declared sweep for an exact tie.

The selected alpha is frozen before evaluating the test split. If the selected
value is 0.5, the existing Hybrid 0.5 test run is reused rather than evaluating
the same configuration twice.

## Outputs

The official run writes versioned, reviewable artifacts:

```text
data/eval/retrieval_v1.jsonl
reports/benchmark_v1_manifest.json
reports/retrieval_baseline_v1.json
reports/retrieval_baseline_v1.md
```

Raw corpora, SQLite databases, and FAISS files remain ignored. The frozen eval
set and reports are allowed into Git so another person can inspect the exact
queries, provenance, aggregate metrics, and per-query results.

The JSON report includes query-type breakdowns and deterministic error groups:

- `hybrid_success_bm25_failure`
- `hybrid_success_dense_failure`
- `dense_success_bm25_failure`
- `bm25_success_dense_failure`
- `all_methods_failure`

Representative examples are the first three records in frozen query order,
not manually selected examples.

## Reproducibility Gates

Before a run can receive the `benchmark_v1` status, the runner requires:

- 50,000 arXiv CS papers.
- 150 queries with the exact 50/100 split and 50/50/50 type distribution.
- Every source paper and relevant paper ID present in SQLite.
- Equal chunk, FTS row, FAISS vector, and ID-map counts.
- An ID map that exactly matches SQLite chunk row order.
- A trained 1024-dimensional BGE-M3 index.
- SHA256 hashes for raw corpus and frozen eval file.
- A clean Git worktree and recorded commit.

Otherwise the output is explicitly marked `smoke_or_development`.

## Planned Official Run

```bash
python scripts/download_arxiv.py \
  --size 50000 \
  --strategy category-balanced \
  --min-year 2020 \
  --end-date 2026-08-23 \
  --output data/raw/arxiv_cs_benchmark_v1_50000.jsonl

python scripts/build_metadata_db.py \
  --input data/raw/arxiv_cs_benchmark_v1_50000.jsonl \
  --db data/indexes/benchmark_v1/metadata.sqlite \
  --overwrite

python scripts/build_fts.py \
  --db data/indexes/benchmark_v1/metadata.sqlite

python scripts/build_retrieval_eval.py \
  --db data/indexes/benchmark_v1/metadata.sqlite \
  --output data/eval/retrieval_v1.jsonl

python scripts/build_faiss.py \
  --db data/indexes/benchmark_v1/metadata.sqlite \
  --output-dir data/indexes/benchmark_v1/faiss \
  --batch-size 8

python -m app.eval.retrieval_eval \
  --eval data/eval/retrieval_v1.jsonl \
  --db data/indexes/benchmark_v1/metadata.sqlite \
  --index-dir data/indexes/benchmark_v1/faiss \
  --raw data/raw/arxiv_cs_benchmark_v1_50000.jsonl
```

The eval set and implementation must be reviewed and committed before the last
command so the manifest can identify an exact clean code revision.

## Interpretation Limit

Benchmark v1 is a synthetic known-item benchmark: each query is generated from
the target paper's title and abstract. It is useful for controlled comparisons
between retrievers, but it is not equivalent to human relevance judgments or a
standard public information-retrieval benchmark.
